# 1. مقدمة عامة

## 1.1 تعريف المشروع
**"سكني" (Sakani)** هي منصة عقارية ذكية متكاملة مصممة خصيصاً للسوق الجزائري. تجمع بين البحث عن العقارات، حجز الحرفيين، إدارة العقود الرقمية، والمحفظة الإلكترونية، مع مساعد ذكي يعمل بالذكاء الاصطناعي.

## 1.2 الأهداف
- **رقمنة سوق الإيجار الجزائري** الذي لا يزال يعتمد بشكل كبير على الوسائل التقليدية
- **توفير بيئة آمنة** للمعاملات العقارية عبر نظام تحقق من الهوية (KYC) وعقود رقمية
- **ربط المستأجرين بالمالكين والحرفيين** عبر منصة واحدة
- **تبسيط إدارة العقارات** للمالكين والوكالات العقارية
- **دعم وسائل الدفع المحلية** (CCP, BaridiMob, Dahabia)

## 1.3 الجمهور المستهدف
| الفئة | الوصف |
|-------|-------|
| المستأجرون (Tenants) | أشخاص يبحثون عن سكن للإيجار |
| المالكون (Owners) | أصحاب عقارات يريدون تأجيرها |
| الحرفيون (Handymen) | مقدمو خدمات صيانة (سباكة، كهرباء، نجارة...) |
| الوكالات العقارية | مكاتب عقارية تريد إدارة عقاراتها رقمياً |
| المشرفون (Admins) | إدارة المنصة والتحقق والمدفوعات |

# 2. الإشكالية والحل المقترح

## 2.1 الإشكالية
- **غياب منصات عقارية متكاملة** في الجزائر تجمع البحث والتعاقد والدفع
- **انعدام الثقة** بين المستأجر والمالك بسبب غياب آليات التحقق
- **صعوبة إيجاد حرفيين موثوقين** عند الحاجة لصيانة المنزل
- **المعاملات النقدية فقط** دون سجل رقمي يحمي حقوق الطرفين
- **عدم وجود عقود رقمية** قابلة للتتبع والمراجعة

## 2.2 الحل المقترح
منصة "سكني" تقدم:
1. **بحث ذكي** عن العقارات بالذكاء الاصطناعي (بالعربية والدارجة)
2. **نظام KYC** للتحقق من هوية المستخدمين
3. **عقود رقمية** قابلة للتوقيع الإلكتروني والتصدير PDF
4. **محفظة رقمية** مع دعم وسائل الدفع الجزائرية
5. **خريطة تفاعلية** لعرض العقارات جغرافياً
6. **نظام تقييمات ومراجعات** لبناء الثقة
7. **إشعارات فورية** للتنبيهات والتحديثات

# 3. البنية التقنية (Technical Architecture)

## 3.1 مكدس التقنيات (Technology Stack)

### الواجهة الأمامية (Frontend)
| التقنية | الاستخدام | السبب |
|---------|----------|-------|
| **React 18** | إطار واجهة المستخدم | مكونات قابلة لإعادة الاستخدام، Virtual DOM |
| **TypeScript** | لغة البرمجة | أمان الأنواع، أخطاء أقل |
| **Vite** | أداة البناء | سرعة فائقة في التطوير والبناء |
| **Tailwind CSS** | التنسيق | كتابة CSS سريعة ومتجاوبة |
| **Framer Motion** | الحركات | تأثيرات حركية سلسة |
| **React Query (TanStack)** | إدارة البيانات | تخزين مؤقت ذكي، مزامنة تلقائية |
| **Zod** | التحقق من المدخلات | تحقق آمن ومحدد النوع |
| **Recharts** | الرسوم البيانية | عرض إحصائيات بصرية |
| **Leaflet** | الخرائط | خرائط تفاعلية مفتوحة المصدر |
| **jsPDF** | تصدير PDF | إنشاء عقود PDF احترافية |

### الواجهة الخلفية (Backend)
| التقنية | الاستخدام | السبب |
|---------|----------|-------|
| **Supabase** | قاعدة بيانات + مصادقة + تخزين | حل متكامل، مفتوح المصدر |
| **PostgreSQL** | قاعدة البيانات | قوية، علائقية، RLS |
| **Edge Functions (Deno)** | دوال سحابية | منطق الأعمال في الخادم |
| **Row Level Security (RLS)** | أمان البيانات | حماية على مستوى الصف |

### تطبيق الهاتف (Mobile)
| التقنية | الاستخدام |
|---------|----------|
| **Capacitor** | تحويل التطبيق لتطبيق أصلي iOS/Android |
| **@capacitor/camera** | الوصول للكاميرا |
| **@capacitor/geolocation** | تحديد الموقع |
| **@capacitor/push-notifications** | الإشعارات الفورية |
| **@capacitor/haptics** | ردود الفعل اللمسية |
| **@capacitor/share** | مشاركة المحتوى |

### خدمات الذكاء الاصطناعي
| التقنية | الاستخدام |
|---------|----------|
| **Lovable AI Gateway** | بوابة نماذج الذكاء الاصطناعي |
| **Google Gemini 2.5 Flash** | نموذج المحادثة والبحث الذكي |

## 3.3 نمط التصميم المعماري

المشروع يتبع **نمط SPA (Single Page Application)** بدون React Router تقليدي، بل يستخدم **نظام شاشات (Screen-based Navigation)** مدار بحالة داخلية:

```typescript
type AppScreen = 
  | 'splash' | 'auth' | 'role-selection' | 'kyc' | 'home' | 'map' 
  | 'settings' | 'properties' | 'property-detail' | 'handymen' | ...;
```

**سبب هذا الاختيار:** التطبيق مصمم كتطبيق هاتف أصلي (Capacitor)، والتنقل بالحالة الداخلية يعطي تحكم أكبر بالانتقالات الحركية ولا يحتاج لتاريخ المتصفح.

| `admin_verify_kyc(...)` | اعتماد/رفض KYC (للمشرفين فقط) |
| `give_phone_consent(contract_id)` | منح إذن مشاركة الهاتف |
| `revoke_phone_consent(contract_id)` | سحب إذن مشاركة الهاتف |
| `is_property_featured(id)` | هل العقار مميز؟ |
| `has_agency_subscription(id)` | هل لديه اشتراك وكالة؟ |

# 7. نظام المصادقة والأمان

## 7.1 نظام المصادقة
- **Supabase Auth** بالبريد الإلكتروني وكلمة المرور
- **JWT Tokens** للجلسات مع تجديد تلقائي
- **Trigger `handle_new_user`:** ينشئ ملفاً شخصياً ودور `user` تلقائياً

## 7.2 Row Level Security (RLS)
كل جدول محمي بسياسات RLS:
- المستخدمون يرون بياناتهم فقط
- المشرفون يرون كل شيء
- بعض البيانات عامة (عقارات متاحة، تسعيرة)

**مثال - جدول profiles:**
```sql
-- المستخدم يرى ملفه فقط
CREATE POLICY "Users can view own profile" ON profiles
FOR SELECT USING (auth.uid() = user_id);

-- المشرف يرى الكل
CREATE POLICY "Admins can manage all profiles" ON profiles
FOR ALL USING (has_role(auth.uid(), 'admin'));
```

## 7.3 نظام KYC (التحقق من الهوية)
1. المستخدم يرفع: صورة الهوية (أمام + خلف) + سيلفي
2. الملفات تُخزن في `kyc-documents` bucket (خاص)
3. المشرف يراجع عبر `admin_get_kyc_verification()`
4. يقبل أو يرفض عبر `admin_verify_kyc()`
5. كل وصول مسجل في `kyc_access_audit`

## 7.4 حماية الهاتف
- الهاتف **مخفي تماماً** بشكل افتراضي
- يظهر فقط عند:
  1. المستخدم يرى ملفه الشخصي
  2. المشرف يعرض الملف
  3. عقد نشط مع **موافقة متبادلة** من الطرفين

## 7.5 حاويات التخزين (Storage Buckets)
| الحاوية | الوصف | عامة؟ |
|---------|-------|-------|
| `property-media` | صور العقارات | ✅ نعم |
| `payment-proofs` | إثباتات الدفع | ❌ لا |
| `kyc-documents` | وثائق الهوية | ❌ لا |

# 11. أسئلة وأجوبة متوقعة من اللجنة

## أسئلة تقنية

### س1: لماذا اخترتم React بدلاً من Angular أو Vue؟
**ج:** React هو الأكثر شيوعاً في عالم الويب مع مجتمع ضخم ونظام إيكولوجي غني. استخدامه مع TypeScript يوفر أمان الأنواع. كما أن Capacitor يدعمه بشكل ممتاز لتحويله لتطبيق أصلي.

### س2: لماذا Supabase بدلاً من Firebase؟
**ج:** Supabase مبني على PostgreSQL المفتوح المصدر مما يعني:
- ملكية كاملة للبيانات
- Row Level Security (أمان على مستوى الصف) - أقوى من Firebase Rules
- دوال SQL مخزنة لمنطق الأعمال المعقد
- إمكانية الاستضافة الذاتية
- دعم أفضل للبيانات العلائقية المعقدة

### س3: لماذا لا تستخدمون React Router؟
**ج:** التطبيق مصمم كتطبيق هاتف أصلي (Capacitor). التنقل بالحالة الداخلية (State-based) يعطينا:
- تحكم كامل بالانتقالات الحركية (AnimatePresence)
- عدم الحاجة لتاريخ المتصفح
- أداء أفضل في التطبيقات الأصلية
- تجربة أقرب للتطبيقات الأصلية

### س4: كيف تضمنون أمان البيانات؟
**ج:**
1. **RLS:** كل جدول محمي بسياسات على مستوى الصف
2. **JWT:** مصادقة آمنة مع تجديد تلقائي للرموز
3. **KYC:** تحقق من الهوية مع سجل وصول
4. **تخزين آمن:** وثائق KYC وإثباتات الدفع في buckets خاصة
5. **حماية الهاتف:** يظهر فقط بموافقة متبادلة
6. **SECURITY DEFINER:** دوال SQL تعمل بصلاحيات محددة

### س5: كيف يعمل الذكاء الاصطناعي؟
**ج:**
1. المستخدم يكتب رسالة (بالعربية أو الدارجة)
2. Edge Function تحلل النية (عقار؟ حرفي؟ أي مدينة؟)
3. تستعلم من قاعدة البيانات الحقيقية
4. تبني سياقاً يحتوي البيانات الحقيقية
5. ترسل للنموذج (Gemini 2.5 Flash) عبر بوابة آمنة
6. النموذج يجيب مع روابط داخلية قابلة للنقر
7. **مهم:** لا يختلق بيانات - يجيب فقط مما هو موجود فعلاً

### س6: ما هو نظام العربون (Escrow)؟
**ج:** 
1. المستأجر يحجز مبلغاً من محفظته → يُخصم من الرصيد ويُضاف للرصيد المحجوز
2. المالك يتحقق من الدفع
3. المشرف يحرر المبلغ → يُحذف من المحجوز ويُضاف لمحفظة المالك
4. كل خطوة مسجلة في `wallet_transactions`

### س7: كيف تتعاملون مع الوقت الحقيقي (Realtime)؟
**ج:** Supabase Realtime عبر WebSocket:
- الرسائل الفورية: `postgres_changes` على جدول messages
- كشف التغييرات تلقائياً

## أسئلة عن النموذج الاقتصادي

### س8: كيف ستربحون من هذه المنصة؟
**ج:** ثلاثة مصادر إيرادات:
1. تمييز الإعلانات (500-1500 دج)
2. اشتراكات الوكالات (2000-10000 دج/شهر)
3. خدمات التوثيق (2000-8000 دج)

### س9: لماذا لا تستخدمون بوابة دفع إلكترونية؟
**ج:** السوق الجزائري يعتمد بشكل كبير على CCP و BaridiMob. بوابات الدفع الإلكتروني محدودة في الجزائر. لذلك اعتمدنا نظام تحويل يدوي مع رفع إثبات الدفع ومراجعة إدارية.

# 12. سيناريوهات "ماذا لو"

## ماذا لو أزلنا نظام المصادقة (AuthContext)؟
**النتيجة:**
- ❌ لا يمكن لأي مستخدم تسجيل الدخول
- ❌ جميع استعلامات Supabase ستفشل (RLS يعتمد على `auth.uid()`)
- ❌ لا يمكن إنشاء عقود أو محادثات
- ❌ التطبيق يصبح غير قابل للاستخدام تماماً

## ماذا لو أزلنا RLS من قاعدة البيانات؟
**النتيجة:**
- ⚠️ كل مستخدم يمكنه رؤية بيانات جميع المستخدمين
- ⚠️ يمكن حذف/تعديل بيانات الآخرين
- ⚠️ وثائق KYC الحساسة تصبح مكشوفة
- 🚨 **كارثة أمنية كاملة**

## ماذا لو أزلنا Edge Function الخاصة بالـ Chat؟
**النتيجة:**
- ❌ المساعد الذكي لن يرد
- ✅ باقي التطبيق يعمل بشكل طبيعي
- ❌ البحث الذكي بالذكاء الاصطناعي لن يعمل
- ✅ البحث اليدوي بالفلاتر لا يزال متاحاً

## ماذا لو أزلنا Capacitor؟
**النتيجة:**
- ✅ التطبيق يبقى يعمل كموقع ويب
- ❌ لا يمكن نشره كتطبيق أصلي على App Store / Play Store
- ❌ الميزات الأصلية (كاميرا، GPS، إشعارات Push) لن تعمل
- ✅ يمكن استخدامه كـ PWA

## ماذا لو أزلنا نظام المحفظة؟
**النتيجة:**
- ❌ لا يمكن دفع تمييز الإعلانات
- ❌ نظام العربون لن يعمل
- ✅ العقود والمحادثات تبقى تعمل
- ❌ النموذج الاقتصادي يخسر مصدر إيرادات

## ماذا لو أزلنا React Query (TanStack Query)؟
**النتيجة:**
- ⚠️ لا تخزين مؤقت ذكي للبيانات
- ⚠️ كل تغيير شاشة يعيد تحميل البيانات
- ⚠️ أداء أبطأ
- ✅ يمكن استبداله بـ useEffect + useState (لكن أقل كفاءة)

## ماذا لو أزلنا Framer Motion؟
**النتيجة:**
- ✅ التطبيق يعمل بشكل كامل
- ❌ لا حركات أو انتقالات سلسة
- ❌ تجربة المستخدم أقل جاذبية
- ✅ حجم التطبيق أصغر

## ماذا لو أزلنا نظام KYC؟
**النتيجة:**
- ⚠️ لا يمكن التحقق من هوية المستخدمين
- ⚠️ مخاطر احتيال أعلى
- ⚠️ لا شارة "موثق" للمستخدمين
- ✅ تسجيل واستخدام أسرع
- ❌ ثقة أقل بين المستخدمين
